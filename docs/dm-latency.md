# DM 응답 지연 분석

2026-11-01. Meta 진단·실제 DM을 반복 호출하지 않고 코드와 최근 운영 로그 50건을 확인했다. 해당 로그에는 세부 처리 시간이 없어 운영 평균·중앙값이나 개선율을 계산할 근거는 없다.

## 확인한 대기와 수정

| 구간 | 기존 흐름 | 변경 |
| --- | --- | --- |
| 콘텐츠 결과 | Gemini 완료 후 대화 기록 읽기·쓰기를 기다림 | 전달 후 같은 `waitUntil` 작업 안에서 기록을 저장함 |
| 전체 DM | 발신자 저장 → OpenAI 검색 임베딩 → 결과 DB 저장 → 받는 방식 조회 → DM | 받는 방식 확인 → 전체 DM → 임베딩·결과 저장. 외래키 순서·실패 처리·전송 확인을 유지함 |
| 일반 채팅 | 답변 생성 후 암호화 대화 기록 저장까지 기다림 | 답변 전송 후 기록 저장. 다음 질문을 위한 과거 기록 읽기는 유지함 |
| 고유 링크 | 결과 저장 후 링크 전송 | 유지. 저장한 ID가 있어야 유효한 링크를 만들 수 있음 |

저장은 생략하지 않는다. Vercel의 `waitUntil` 작업이 기록·검색 색인까지 기다린다. 전체 DM 뒤 대시보드 반영까지 짧은 간격이 생길 수 있다. 저장 장애 시 DM은 이미 전달되어도 카드가 남지 않을 수 있어 기존 저장 오류를 기록한다. 실패·전송 불확실 메시지의 자동 재시도는 기존처럼 하지 않는다(중복 방지를 위한 durable outbox는 별도 과제).

## 모델·원본 처리 시간

실제 Gemini `gemini-3.8-flash`에 가상 미용실 본문을 **한 번** 보낸 확인에서는 모델 호출 10,251ms, 결과 정규화까지 10,253ms였다. 이미지·영상·Instagram 전송 시간을 포함하지 않는 단일 표본이므로 운영 DM 평균으로 해석하면 안 된다. 검증 내용은 `.local/beauty-gemini-smoke.json`에 로컬 저장했다.

배포 후 사용자가 실제 Instagram에서 **미용 버튼과 정리 결과를 모두 수신**했다고 확인했다. 해당 배포의 `action: beauty`, `status: done` 운영 기록 한 건에서는 다음 시간이 관측됐다.

| 측정 구간 | 시간 |
| --- | --- |
| 첫 접수 답장 전송 확인 | 1.9초 |
| 원본 다운로드·변환·임시 저장 (`prepare_ms`) | 23.5초 |
| Gemini 호출 (`model_ms`) | 12.9초 |
| 분석 후 임시 파일 정리 | 1.9초 |
| 전체 결과 DM 전송 확인 (`result_sent_ms`) | 처리 시작 후 44.1초 |
| 답장 뒤 임베딩·결과 저장 단계 | 0.8초 |

이번 건의 큰 대기는 원본 확보와 모델 생성이었다. 합계가 별도인 단계와 포함 관계를 혼동하면 안 된다. DM 기준은 아래 로그 설명대로 웹훅 기록·토큰 로딩 이후이며, 전체 결과 시간에 각 단계가 포함된다. 저장 단계 시간만으로 DB 저장 성공을 별도 입증한 것은 아니고, 대시보드에 실제 카드가 보이는지는 이번 확인에서 직접 관찰하지 않았다. 단일 사례라 평균·개선율을 뜻하지 않는다. 같은 배포에 `no_input` 결과도 있어 원본 확보 제한이 해소됐다고 해석하면 안 된다. 원본 로그는 비공개 로컬 파일에만 보관하고 문서에는 내용·계정·URL을 기록하지 않는다.

구조상 다음 비용은 남는다. 원본 주소 확인, 다운로드·변환·비공개 임시 저장, 최대 10개 파일 읽기, 멀티모달 Gemini 생성, AI 완료 후 임시 파일 삭제, Meta 메시지의 순서 있는 전송이다. 뉴스는 주장 추출·근거 검색·판정이 필요해서 레시피/미용 같은 한 번의 추출보다 단계가 많다. 원본이 없으면 다운로드를 무한 반복하지 않고 현재 한계를 안내한다.

일반 채팅은 기존 `gemini-3.5-flash-lite` minimal 설정을 유지하고 콘텐츠 모델/분석 범위를 낮추지 않았다. 모델 추론 수준 변경은 품질과 지연의 교환이므로 이번에 일괄 적용하지 않았다. [Google 추론 수준 안내](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/thinking)

## 원본 준비 단계 개선과 운영 비교

2026-11-01, 동일한 공개 게시물을 기존 배포와 개선 배포에서 **각각 한 번씩** 준비했다. Gemini·Meta Graph API·실제 DM 발송은 호출하지 않았다. 기존 최고 해상도 이미지 선택·JPEG 변환·영상 포맷·미디어 개수 제한은 바꾸지 않고 다운로드와 업로드의 대기를 겹쳤다.

| 측정 | 기존 | 개선 |
| --- | --- | --- |
| 원본 준비 API의 응답까지 | 44,602ms | 19,407ms |
| AI 입력 파일 | 이미지 7장 + MP4 1개 | 동일한 8개, 순서·크기·SHA-256 모두 일치 |
| AI 입력 읽기 중 보존된 비공개 객체 | 16개 | 16개 |
| 입력 소비 후 남은 임시 객체 | 0개 | 0개 |

이 한 번의 비교에서는 56.5% 단축됐다. 앞서 미용 DM에서 관측한 전체 44.1초와 **다른 게시물의 원본 준비 단계** 비교이므로, 전체 DM이 19.4초로 줄었다는 뜻이 아니다. 콜드 스타트·원본 응답 차이가 포함된 단일 표본이며 평균 개선율은 측정하지 않았다. 새 배포의 상세 시간은 메타데이터 2,242ms, 파일 전송 946ms, 비공개 저장·변환 14,370ms, 이전 작업 복구 878ms다. 이전 작업 복구는 새 작업과 겹친다. 남은 큰 대기는 비공개 저장 단계다.

자동 검증은 동시 작업 상한 3개, 10개 혼합 미디어의 순서 보존, 누락·중복·한도 초과 거절, 부분 실패 후 늦은 업로드까지 끝난 다음 정리, AI 종료 전 원본 유지 등을 포함한다. 로컬에서 Python 25개·Node 229개와 빌드가 통과했고 CI도 Windows/Ubuntu에서 통과했다. 비교 보고서와 원본 해시는 공개 저장소가 아닌 `.local/media-speed-comparison.json`에만 보관한다.

## 단일 릴스 경로 개선과 운영 비교

단일 영상은 원본을 Python에서 내려받아 Blob에 업로드한 다음 Node가 다시 내려받는 왕복을 줄였다. 기존과 같은 `b[ext=mp4]/b` 통합 포맷을 선택하고, 정확히 한 개의 직접 MP4라면 Node 메모리로 전체 파일을 받는다. AI 완료 또는 실패 후 버퍼를 0으로 덮어쓴다. 여러 항목·분리 트랙·HLS·직접 다운로드 오류는 기존 전체 임시 저장 경로로 처리한다. Instagram의 `acodec` 이름 생략은 실제로 음성을 제거했다는 뜻이 아니므로 원래 포맷 선택 결과를 유지한다.

2026-11-01 같은 공개 릴스로 기존 경로와 최종 직접 경로를 비교했다.

| 측정 | 기존 임시 저장 | 직접 MP4 |
| --- | --- | --- |
| 준비 API/다운로드 반환 | 8,160ms | 4,016ms |
| 전체 영상이 AI 입력으로 읽힌 시점 | 9,397ms | 4,017ms |
| 영상 크기 | 8,049,062bytes | 동일, SHA-256도 일치 |
| 분석 입력을 보관한 비공개 객체 | 2개 | 0개: 메모리에서 보관 |
| 정리 후 비공개 객체 | 0개 | 0개, 메모리 버퍼도 0으로 덮어씀 |

이 사례에서는 AI 입력 준비 시간이 57.3% 단축됐다. 최종 경로의 메타데이터 확보는 2,671ms, 직접 전송은 713ms였다. 코덱 이름 생략으로 최적화가 적용되지 않는 사례는 중간 검증에서 발견해 보완했다. 원본·영상·음성을 자르거나 재인코딩한 변화는 없다. 이번 비교는 Gemini 분석·실제 DM 전송을 추가 호출하지 않은 준비 단계 측정이며, 전체 답장 시간이나 여러 영상의 평균을 뜻하지 않는다. 로컬 보고서는 `.local/reel-speed-comparison.json`에 보관한다.

최종 회귀 검증은 Node 236개·Python 30개와 Windows/Ubuntu CI가 통과했다. 서명·원본 URL 일치·최종 CDN·MP4 바이트·20MiB 한도, 작업별 접근 제한, 성공/모델 실패 후 메모리 정리, 직접 다운로드 오류의 한 번만 실행되는 전체 경로 복귀도 검증한다. 임시 저장을 생략하는 경로에서도 원본 전체는 AI 처리 종료까지 유지한다.

## 이후 로그 확인

- `DM_TIMING`: `token_ms`, `first_response_ms`(Meta가 첫 답장 수락), `analysis_ms`, `preference_ms`, `save_ms`(임베딩 포함), `result_sent_ms`(전체 결과 전송 확인), `total_ms`.
- `MEDIA_TIMING`: `shared_video_ms`, `resolve_ms`, `prepare_ms`, `analysis_ms`, `cleanup_ms`, `total_ms`. 수행한 단계만 기록한다.
- `AI_TIMING`: 모델·chat/structured·성공 여부·`model_ms`. 실제 모델 요청마다 한 건.
- Python `MEDIA_PREP_TIMING`: `sdk_ms`, `metadata_ms`, `transfer_ms`, `lease_ms`, `download_ms`, `stage_ms`, `purge_ms`, `handler_ms`. 다운로드는 3개씩, 저장 작업도 3개씩 겹쳐 수행하며 JPEG 변환 메모리는 한 장으로 제한한다. 오래된 작업 복구는 새 작업과 겹쳐 실행한다. 모든 파일·원본 품질·AI 완료 후 삭제 계약을 유지한다.

본문·발신자 ID·메시지 ID·미디어/원본 URL·키는 이 로그에 넣지 않는다. DM의 시간 기준은 토큰을 읽은 뒤 유효한 메시지 처리를 시작한 시점이다. Meta에서 우리 서버까지의 전달 지연, 웹훅 수신 기록 저장, 사용자 기기의 표시 지연은 포함하지 않으며 `token_ms`는 별도 값이다. `analysis_ms`는 선택 티켓과 미디어 전처리까지 포함하므로 `MEDIA_TIMING`/`AI_TIMING`을 다시 더하지 않는다. 서로 다른 요청의 로그가 섞일 수 있으므로 현 단계의 집계는 단계별 분포를 확인하는 용도다.

자동 테스트는 저장을 강제로 대기시켜도 전체 DM이 먼저 전달되고, 고유 링크는 저장을 기다리며, 지연한 대화 기록 작업도 종료 전에 수행됨을 확인한다. 실제 Instagram 화면의 새 미용 선택과 결과 도착 시간은 사용자가 새 게시물을 한 번 공유해 확인하면 된다.
