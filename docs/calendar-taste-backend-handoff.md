| 순서 | 백엔드 작업 | 완료되면 달라지는 경험 |

우선 1~4를 연결하면 된다. Gemini 분석·색인·검색·관심 추정은 이미 있으므로 새로 만들 필요가 없다. 서버 API 구현 후 아래 프론트 연결 지점을 함께 수정해야 실제 동작이 바뀐다.

## 프론트 적용 상태

- `/taste`: 제공 디자인의 취향 궤도·분야 필터·선택 카드·콘텐츠 열기·취향에서 빼기를 PC/모바일에 적용했다. 직접 모은 정리 완료 레시피·전시/공간·공모전/대외활동·맛집을 네 궤도로 표시한다. 취향공간은 전시/공간에 함께 묶고 뉴스/정보는 제외한다. 목록은 모두 표시하고, 행성은 분야마다 최대 8개다.
- `/calendar`: 사이드바에서 내 취향 다음, 모바일에서는 네 번째 하단 탭이다. 월/주 전환·이전/다음·오늘·유형 필터·날짜 선택·콘텐츠 요약·일정 추가/수정/삭제가 동작한다.
- 실제 모드의 선택 목록은 로그인 계정이 볼 수 있는 정리 완료 레시피·전시·공모전·맛집·취향공간이다. 캘린더는 전체 + 5개 유형 탭을 사용한다. 뉴스·미처리 결과는 일정 등록 대상이 아니다.
- 현재 대시보드가 불러오는 최근 200개 결과가 선택 범위다. 제외되거나 현재 불러오지 못한 콘텐츠의 일정은 화면에서 숨기고 로컬 원본은 남긴다. 서버 캘린더는 최근 콘텐츠 목록과 별개로 참조 항목을 조회해야 오래된 일정도 정상 표시된다.
- 지금 일정은 `localStorage`의 `dimi-calendar:v1:<auth-user-id>`에 계정별로 저장한다. **서버 저장·다른 기기 동기화는 아직 없다.** 기존 수동 취향도 `inthon-taste:<auth-user-id>`에 남아 있다.
- **실제 DM 리마인드는 보내지 않는다.** 실제 모드의 전송 스위치/알림 옵션은 비활성화했고, 준비 중 안내를 표시한다. 데모의 알림 예약/미리보기는 예시다.
- 기존 Gemini 색인·검색·관심 추정 API와 데이터는 유지한다. 새 궤도의 수동 모음과 AI 관심 추정을 같은 데이터로 덮어쓰지 않는다.

### 분류별 연결 기준

| 원본 `type` | 내 취향 궤도 | 캘린더 탭 | 허용 일정 `kind` |
| --- | --- | --- | --- |
| `recipe` | 레시피 | 레시피 | `cook` |
| `exhibit` | 전시·공간 | 전시·팝업 | `visit` |
| `contest` | 공모전·대외활동 | 공모전·대외활동 | `deadline`, `prep`, `result` |
| `restaurant` | 맛집 | 맛집 | `visit` |
| `space` | 전시·공간에 함께 표시 | 취향공간 | `visit` |
| `news` | 제외 | 제외 | 없음 |
| `beauty` | 제외 | 제외 | 없음 |

취향은 4개 그룹이고 캘린더는 5개 유형이다. 화면에서 함께 묶는다고 저장된 `space`를 `exhibit`로 바꾸면 안 된다. 즐겨찾기(`state.fav`)와 직접 모은 취향(`state.taste`)도 별도 상태다.

### 콘텐츠 식별자: 게시물 ID와 개별 카드 ID를 구분

현재 `factchecks`의 한 행에서 여러 전시·맛집·공간 카드가 만들어질 수 있다. `fc42`는 42번 결과의 첫 카드, `fc42-2`는 두 번째 카드다. 접미사는 이미지 장수가 아니라 **분석 결과 내 개별 항목의 순서**다.

- 서버는 `content_id`에서 `factcheck_id`와 1부터 시작하는 항목 순서를 확인하고, 해당 유형의 결과에 그 항목이 실제로 있는지 검증한다.
- 여러 카드가 있는 결과를 재분석할 때 순서를 바꾸면 기존 참조가 깨진다. 현재 결과를 임의로 재정렬하지 말고, 향후 재분석을 지원할 때 안정적인 하위 항목 ID와 이전 ID 매핑을 함께 도입한다.
- 취향 추가/제거와 일정은 개별 카드 단위다. 현재 내 콘텐츠의 삭제/숨김은 `rowIdOf()`로 부모 행 전체에 적용되므로 두 동작을 혼동하지 않는다.
- 최근 200개 밖의 참조는 사용자 권한으로 원본 행을 별도 조회하고 기존 변환 함수를 재사용한다. 전체 게시물의 제목/색인을 두 번째 카드의 제목/색인으로 복사하지 않는다.

## 1순위: 사용자 일정 CRUD와 소유권

권장 레코드(아래 이름은 API 제안이며, 마이그레이션을 실행하지 않았다):

```json
{
  "id": "server-uuid",
  "content_id": "fc42-2",
  "kind": "visit",
  "date": "2026-11-07",
  "time": "14:00",
  "timezone": "Asia/Seoul",
  "revision": 1
}
```

- 인증 UID는 검증된 세션에서 결정한다. 요청 본문의 `user_id`·Instagram 핸들로 소유권을 정하지 않는다. 사용자별 읽기/쓰기 RLS가 필요하다.
- 기존 `factchecks` 행 ID와 `content_id`의 하위 항목 번호를 함께 보존한다. **`fc42`와 `fc42-2`는 다른 전시**다. 행 ID만 저장하면 여러 장 게시물의 다른 전시가 서로 연결된다.
- 참조 콘텐츠가 현재 사용자 소유·접근 가능·정리 완료인지 확인한다. 클라이언트가 보낸 제목·분류를 권한이나 원본 사실로 사용하지 않는다.
- 일정 종류: 레시피 `cook`, 전시·맛집·취향공간 `visit`, 공모전 `deadline / prep / result`. `time: null`은 종일이며 임의의 자정 시각으로 바꾸지 않는다.
- 실제 존재하는 날짜, `HH:mm`, 종류와 콘텐츠 유형의 조합을 검증한다. 알려진 전시 기간/휴무·공고의 확정 날짜를 서버에서도 검증한다. 미확인 날짜·휴무를 추측하지 않는다.
- 일정은 사용자의 계획이다. 전시 예약 완료나 공모전 지원 완료를 뜻하지 않는다.
- 목록은 날짜 범위로 조회하고, 생성 요청에는 재전송 중복 방지 키를 받는다. 수정은 revision/updated_at으로 충돌을 탐지한다. 오류 시 프론트가 기존 일정과 작성 중 값을 유지할 수 있어야 한다.

제안 엔드포인트:

| 요청 | 동작 |
| --- | --- |
| `GET /api/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` | 본인 일정 목록 |
| `POST /api/calendar` | 본인 콘텐츠의 일정 등록 |
| `PATCH /api/calendar/:id` | 본인 일정 수정 |
| `DELETE /api/calendar/:id` | 본인 일정 삭제와 대기 알림 취소 |

`401`은 재로그인, `403/404`는 접근 불가, `409`는 갱신 충돌, `422`는 날짜/콘텐츠 조건 불일치로 구분하면 프론트에 연결하기 쉽다.

### 저장할 최소 데이터

테이블명 `calendar_events` 제안:

| 필드 | 용도 |
| --- | --- |
| `id` | 서버가 부여한 일정 ID. UUID 사용 가능 |
| `user_id` | 검증된 로그인 사용자 UID |
| `factcheck_id`, `item_index` | 기존 결과 행 FK + 1부터 시작하는 하위 항목 순서 |
| `kind`, `date`, `time` | 일정 종류, 한국 날짜, 시각 또는 `null` |
| `timezone` | 우선 `Asia/Seoul` |
| `revision`, `created_at`, `updated_at` | 수정 충돌 감지와 변경 시각 |

`(user_id, date)` 조회를 지원하고, 생성 요청의 중복 방지 키는 사용자별로 구분한다. 같은 콘텐츠를 서로 다른 날짜에 등록할 수 있어야 한다. 저장된 제목만 믿고 권한 없는 콘텐츠를 보여주지 않는다.

등록은 위 레코드 예시에서 `id`·`revision`을 제외한 값으로 요청한다. `Idempotency-Key`는 같은 등록의 재시도 동안 유지한다. 수정 요청에는 읽었던 `revision`을 포함하며 성공 응답은 서버가 확정한 새 레코드다. 삭제는 반복해도 안전하게 처리한다.

조회 응답 형식 제안:

```json
{
  "events": [
    {
      "id": "5e2b6fab-2f58-4df1-bd5e-80065e656a21",
      "content_id": "fc42-2",
      "kind": "visit",
      "date": "2026-11-07",
      "time": "14:00",
      "timezone": "Asia/Seoul",
      "revision": 1
    }
  ],
  "reminders_available": false
}
```

`from`과 `to`는 양끝을 포함하고, 월 보기의 앞뒤 달 날짜까지 실제 표시 범위로 조회한다. 월/주 전환·이전/다음 이동 시 갱신하며 이전 범위의 늦은 응답이 새 화면을 덮어쓰지 않게 한다. 참조 콘텐츠는 응답에 포함하거나 별도 인증된 조회로 제공하되, 목록 밖의 오래된 콘텐츠도 상세를 열 수 있어야 한다.

날짜 검증 시 현재 UI가 실제로 아는 범위를 구분한다. 전시의 정규화된 `start/end`와 공모전의 확정 마감/발표 날짜는 검증에 쓴다. 전시 휴무는 현재 화면에 문자열로 표시되지만 실제 모드의 차단 배열은 비어 있다. 휴무를 강제하려면 신뢰할 수 있는 구조화 데이터가 필요하다. 과거 기록을 가져오기 할 때는 신규 등록의 ‘오늘 이전 차단’을 그대로 적용해 이관 기록을 버리지 않는다.

## 2순위: 수동 취향 동기화

- 사용자 UID + 정확한 하위 콘텐츠 ID를 키로 수동 모음 상태를 저장/조회한다. 모음에서 빼도 분석 원본을 삭제하거나 싫어요로 해석하지 않는다.
- 현재의 색인 기반 관심 추정은 공유 콘텐츠의 반복 특징이다. 수동 모음 테이블과 구분해서 유지한다. 새로운 취향 설문은 추가하지 않는다.
- 로그인 기기마다 숫자와 궤도가 같도록 목록 조회 + 멱등 추가/제거가 필요하다. 새 테이블의 접근도 본인 UID로 제한한다.

테이블명 `taste_collections` 제안: `user_id`, `factcheck_id`, `item_index`, `created_at`. 사용자 + 개별 카드 조합을 유일하게 하며, 원본 제목·AI 색인을 이 테이블에 복제하지 않는다.

| 요청 제안 | 동작 |
| --- | --- |
| `GET /api/taste` | 본인의 모음 목록과 각 카드 참조 반환 |
| `PUT /api/taste/:content_id` | 이미 모았어도 중복 없이 추가 |
| `DELETE /api/taste/:content_id` | 모음 해제. 원본 분석/일정/즐겨찾기는 유지 |

조회 응답 예시:

```json
{
  "items": [
    { "content_id": "fc42-2", "collected_at": "2026-11-01T01:00:00Z" }
  ]
}
```

- 서버 조회 결과를 `{ "fc42-2": true }` 형태의 `state.taste`에 연결하면 기존 궤도 렌더링을 그대로 사용할 수 있다. 추가/해제는 카드별로 요청을 직렬화하고, 실패하면 이전 표시와 숫자를 복구한다.
- 숫자는 실제 접근 가능한 모음의 카드 수다. 궤도 행성이 분야별 최대 8개인 것은 표시 제한이며, 서버 저장 상한이나 총 개수 제한이 아니다. 목록은 페이지를 끝까지 조회하거나 총 개수와 다음 페이지를 명확히 반환한다.
- 모은 카드의 본문도 함께 확보해야 한다. 지금처럼 `app.allItems()`의 최근 200개와 교집합만 취하면 오래된 취향이 사라져 보인다. 오래된 참조 조회를 일정과 함께 해결한다.

### 이미 있는 관심 추정 API와 이번 화면의 차이

- 기존 `POST /api/content-search`에 `{ "action": "interests" }`를 보내면 `{ ids, interests, rankedBy, degraded, query, scope }`를 받는다. 기존 `indexRequest()`의 사용자 JWT 전달을 재사용한다.
- `interests`의 패턴은 `category`, `label`, `count`, `signal: "shared_interest"`, `evidence: [{ id, postId, title, reason }]`이다. `ids`는 본인이 이미 보낸 콘텐츠 중 다시 볼 후보이며 외부 새 콘텐츠 추천 목록은 아니다.
- 현재 추정 범위는 레시피·전시이며, 서로 다른 원본 2개 이상에서 반복된 근거를 사용한다. 맛집·취향공간·공모전은 수동 모음에 들어가지만 자동 추정 대상에는 아직 포함되지 않는다. 같은 게시물의 여러 카드로 표본 수를 부풀리지 않는다.
- **현재 새 취향 디자인은 수동 모음의 궤도·목록을 표시한다.** 기존 API 호출과 `dashboard-index.js`는 남아 있지만, 이 디자인에 관심 추정/추천 카드가 추가로 그려지는 것은 아니다. 추정 UI를 다시 붙일 때는 별도 디자인 연결이 필요하며, 이번 동기화 작업의 필수 범위가 아니다.
- 기존 API의 최근 200개·최대 24개 재정렬·저장 색인 폴백을 유지한다. 수동 취향을 동기화하려고 Gemini 재분석/대량 임베딩을 다시 실행하지 않는다. 자세한 색인 계약은 [content-index.md](content-index.md)를 따른다.

## 3순위: DM 리마인드

서버 저장만 붙이고 프론트 전송 스위치를 켜면 안 된다. 아래까지 준비된 뒤 활성화해야 한다.

1. 현재 Meta 앱 모드·권한·메시지 정책에서 예약 시각의 선제 DM을 보낼 수 있는지 확인한다. 기존 DM 답장이 된다는 사실로 장기 예약 알림도 가능하다고 가정하지 않는다. 불가능한 경우 사용할 다른 알림 채널을 먼저 결정한다.
2. 사용자 동의, 연결 계정과 실제 수신자 매핑, 발송 가능 상태 확인이 필요하다. Instagram 연결 해제·계정 변경·회원 탈퇴 시 대기 전송을 취소한다.
3. 알림 시각은 `Asia/Seoul`의 일정 기준으로 계산한다. 지원 옵션은 당일 09:00, 1시간 전, 전날 20:00, 3일 전 09:00이다. 시간이 없는 일정에는 1시간 전 옵션을 허용하지 않는다.
4. 서버 작업자/스케줄러가 실행하고, `event-id + revision + reminder-kind`로 중복 전송을 막는다. 수정·삭제 시 기존 작업을 무효화한다. 과거 시각의 알림을 즉시 몰아서 보내지 않는다.
5. `pending / scheduled / sending / sent / failed / cancelled / skipped`를 구분하고, 실제 발송 성공 후에만 `sent`를 표시한다. 날짜가 지났다는 이유로 ‘보냄’으로 만들지 않는다.
6. 서버의 발송 자격/설정 가능 여부와 실패 상태를 프론트에 반환한다. 키·토큰은 서버에만 둔다.

프론트 옵션 키는 `day9`(당일 09:00), `h1`(1시간 전), `eve`(전날 20:00), `d3`(3일 전 09:00)다. 현재 로컬 일정은 항상 `dm: false`, `rem: []`로 저장된다. 활성화할 때 실제 서버 발송 이력으로 표시를 바꿔야 한다. 디자인 원본의 ‘예약 시각이 지나면 보냄’ 계산은 데모 로직이므로 운영 발송 상태로 재사용하지 않는다.

## 프론트 연결 지점

- `public/js/dashboard-calendar.js`: 현재 브라우저 저장·계정 전환·실제 콘텐츠 매핑. `createCalendarDashboard`의 읽기/저장을 서버 CRUD로 교체하고 로딩/저장 실패 처리를 유지한다.
- `frontend/calendar/Calendar.dc.html`: 제공 캘린더의 화면/기본 동작 원본. `public/js/calendar-model.js`는 생성물이므로 직접 수정하지 않는다.
- `public/js/dashboard-taste.js`: PC/모바일이 함께 쓰는 궤도·선택·모음 해제. 서버 저장 시 기존 `app.state.taste`와 모음 갱신 경로를 연결한다.
- `frontend/taste-redesign/Taste.fragment.html`, `public/css/taste.css`: 취향 디자인. `scripts/build-dashboard.py`가 PC/모바일 템플릿에 삽입한다.
- 모바일 새 화면은 `frontend/mobile/Mobile.dc.html`의 궤도와 `frontend/mobile/MobileCalendar.fragment.html`을 사용한다. 상태·저장은 같은 `dashboard-taste.js`/`dashboard-calendar.js`를 공유한다. 캘린더의 `values(true)`는 날짜 점·일정 카드 등 모바일 표시만 변환한다.
- 기존 결과 상세의 Google Calendar 링크/방문 날짜 링크는 별도 기능으로 유지했다. 향후 내부 일정 추가로 바꿀지는 백엔드 CRUD 연결 시 결정한다.

### 반드시 함께 바꿀 동작

1. `dashboard-app.js`의 `enterLive()`는 취향을 로컬에서 읽고, `componentDidUpdate()`가 로컬에 저장한다. 조회·추가·해제를 서버로 전환할 때 두 경로와 상세 화면의 취향 버튼, 궤도의 빼기 버튼을 모두 연결한다. PC/모바일이 동일한 서버 상태를 써야 한다.
2. `createCalendarDashboard()`의 현재 `setState()`는 동기 함수다. `CalendarModel.save()`는 반환값이 `false`일 때만 성공 처리·모달 닫기를 중단한다. **여기에 단순히 `async fetch`만 넣으면 Promise를 성공으로 간주해 저장 전에 모달이 닫힌다.** 저장/수정/삭제 액션을 비동기로 연결하고, 확정 응답 뒤에 상태 변경·성공 안내를 한다. 저장 중 중복 클릭을 막고 실패 시 초안을 유지한다.
3. 현재 로컬 일정 형식은 아래와 같다. `item`을 API의 `content_id`로 매핑한다. 로컬 `id`는 증가하는 정수이고 검증기도 정수만 허용한다. 서버 UUID를 사용할 경우 검증기·모달 ID·목록 키·로컬 가져오기를 함께 수정한다. UUID를 숫자로 강제 변환하지 않는다.

```json
[
  {
    "id": 1,
    "item": "fc42-2",
    "kind": "visit",
    "date": "2026-11-07",
    "time": "14:00",
    "dm": false,
    "rem": []
  }
]
```

4. 캘린더의 `constants.CONTENT`는 현재 `app.allItems()`로 구성한다. 서버 일정에 필요한 과거 참조도 채우고, 로그인 사용자 변경 시 조회·초안·이전 계정 응답을 모두 분리한다. 취향도 같은 원칙을 적용한다.
5. 생성 파일인 `public/js/calendar-model.js`, `public/js/dashboard-model.js`, `public/js/mobile-model.js`, `public/data/*-template.json`만 직접 수정하지 않는다. 원본은 `frontend/calendar/Calendar.dc.html`, `frontend/design/Main.dc.html`, `frontend/mobile/Mobile.dc.html`이며, 수정 후 `npm run build`로 생성물을 갱신한다.

## 기존 브라우저 데이터 이관·삭제

- 로그인 후 해당 UID의 로컬 일정과 모음을 한 번 가져와 서버에서 접근 가능한 콘텐츠만 검증해서 이관한다. 반복 실행에도 중복이 생기지 않아야 한다.
- **서버 저장 성공을 확인한 뒤** 로컬 원본을 정리한다. 실패 시 브라우저 원본과 작성 중 값을 남긴다.
- 계정 A의 로컬 데이터를 계정 B로 이관하지 않는다. 다른 기기의 변경과 충돌하면 사용자에게 설명하고 자동 덮어쓰지 않는다.
- 콘텐츠 제외/삭제·연결 해제·탈퇴·보관 기간 만료 때 일정과 알림을 각각 어떻게 처리할지 정한다. 접근 불가 콘텐츠의 일정/모음을 다른 사용자에게 노출하지 않는다.
- 기존 회원 탈퇴 처리에 신규 서버 일정·취향·대기 알림 정리를 추가하고, `dimi-calendar:v1:<uid>`·기존 취향/즐겨찾기 키 정리도 확인한다.
- 취향 로컬 값은 `{ "fc42-2": true, "fc15": false }`다. 오래된 `false` 값을 서버의 최신 모음을 지우는 명령으로 일괄 적용하지 않는다. 서버에 이미 있는 상태를 우선하고, 아직 없는 유효한 모음만 가져오는 방식을 기본으로 한다. 로컬에는 모은 시각이 없으므로 과거 시각을 만들어 저장하지 않는다.
- 서로 다른 브라우저에서 로컬 일정 ID `1`이 겹칠 수 있다. 가져오기 중복 방지 키는 UID + 브라우저/가져오기 식별자 + 로컬 일정 ID로 구분한다. 성공/건너뜀/재시도 항목을 구분해 실패한 항목의 로컬 원본을 먼저 지우지 않는다.

## 인증·권한 연결

기존 결과는 `factchecks.igsid`와 `account_links(user_id, igsid)`의 연결을 통해 현재 로그인 사용자에게 보인다. `factchecks`에 Google UID 컬럼이 직접 있다고 가정하지 않는다. 신규 모음/일정은 검증된 UID를 저장하고, 읽기·쓰기 시 참조 콘텐츠의 현재 접근 권한도 확인한다. 연결 변경 후 과거 계정의 제목·내용을 노출하거나 알림을 보내면 안 된다.

신규 노출 테이블은 역할별 GRANT와 사용자 소유권 RLS를 함께 설정한다. UPDATE는 SELECT 정책 및 `USING`/`WITH CHECK`도 확인한다. 클라이언트에 서버 비밀키를 전달하지 않는다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [Data API 접근 제어](https://supabase.com/docs/guides/api/securing-your-api)를 기준으로 실제 프로젝트 설정을 검증한다.

## 연결 완료 기준

- 같은 계정으로 두 기기에서 같은 일정/모음이 보이고 다른 계정에서는 보이지 않는다.
- 같은 게시물의 전시 두 개를 별도 일정으로 등록해도 섞이지 않는다.
- 등록·수정·삭제 실패 시 이전 값과 초안이 보존된다. 재시도해도 중복 일정/DM이 생기지 않는다.
- 확인된 기간 밖 전시·잘못된 날짜/시각을 서버가 거절하고, 알 수 없는 정보는 미확인으로 남긴다.
- 실제 DM 발송 권한과 정책을 확인하고 예약/전송/취소를 검증한 후에만 리마인드 UI를 활성화한다.
- 맛집·취향공간도 각각 방문 일정 등록·수정·삭제·필터링이 되고 뉴스는 등록되지 않는다.
- 최근 200개 밖의 일정·취향도 조회·상세 열기가 되며, 접근 불가 카드의 내용을 우회 노출하지 않는다.
- 네트워크 지연·새로고침·재로그인·계정 전환·등록 연타·반복 가져오기에서 중복이나 데이터 손실이 없다.
- 서버 장애를 빈 목록 성공으로 저장하거나 로컬 기록을 덮어쓰지 않는다. 기존 계정·연결 해제·탈퇴 흐름도 함께 확인한다.
