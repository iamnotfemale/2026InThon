# 콘텐츠별 처리 계약

공통 흐름은 원본 확보 → 선택한 처리기 → 구조 검증 → 완료 결과 저장 → 개인 링크 DM이다. 사용자가 누른 버튼으로 바로 분기하므로 별도 AI 분류 호출을 하지 않는다. 팩트체크는 근거 검색이 필요하지만 레시피에는 검색·사실 판정 단계를 실행하지 않는다.

| 구분 | 구조 | 현재 상태 |
| --- | --- | --- |
| 레시피 | 요리명, 요약, 인분, 준비·조리·전체 시간, 재료·분량·선택 여부, 단계·불세기·온도·지속시간, 원문 팁, 확인사항 | 구현·실제 두 콘텐츠 검증 |
| 뉴스·정보 | 검증 주장, 판단, 이유, 직접 확인한 근거 링크, 한계 | 기존 팩트체크 유지 |
| 전시·팝업 | 행사명, 소개, 기간(원문 날짜 포함), 운영 시간·휴무, 장소·주소, 입장료, 예약, 관람 조건, 예약·공식 링크, 확인사항 | 구현 (일정 조회 → 전시 분기) |
| 공모전·대외활동 | 공고명, 종류, 소개, 주최·주관·후원, 일정(접수 시작·마감·발표·활동·행사, 날짜·시간), 지원 대상·조건, 제출물, 지원 절차, 혜택·참가비, 문의처, 공고·신청 원본 링크, 확인사항 | ‘일정 조회’로 구현 |
| 맛집 | 상호, 분류, 소개, 동네·주소, 전화, 영업 시간·휴무, 가격대, 예약·웨이팅·주차, 메뉴(원문 가격·원 단위 가격·설명·대표 여부), 원본 링크, 근거, 확인사항 | ‘맛집 정리’로 구현, **전용 테이블** |
| 취향공간 | 상호, 분류, 소개, 동네·주소, 전화, 운영 시간·휴무, 예약·대기·주차, 원본 링크, 근거, 확인사항 (맛집에서 메뉴·가격 제외) | ‘취향공간 정리’로 구현, v1 JSON |

값이 없으면 null로 둔다. 날짜·마감 시간을 추정하지 않고, 오래된 콘텐츠를 현재 모집 중이라고 단정하지 않는다. 미래 일정 처리기에서도 정보별 출처와 충돌·누락을 보존한다. 링크는 모델이 생성한 것을 그대로 믿지 않고 실제 확보한 원본에서만 채택한다.

## 공모전·대외활동 구현

‘일정 조회’ 버튼은 전시·팝업과 공유한다. 한 번의 Gemini 호출이 `kind`(contest·activity·exhibit·none)를 함께 판별하고, 전시·팝업이면 아래 전시 처리기로 넘기고, 모집 정보가 없으면 그 사유를 답한다.

- `contest.mjs`: 프롬프트, 이미지·영상·본문 동시 분석(레시피와 같은 미디어 확보·삭제 흐름), DM 렌더링, 접수 안내 문구.
- `public/js/contest-data.js`: 서버·클라이언트 공용. 모델 출력 정규화(`normalizeContest`), v1 검증(`validateContest`), 화면 시점 계산(`contestTimeline`), Google 캘린더 링크.
- **날짜:** 모델은 원문 표기(`raw`)와 숫자(연·월·일, 24시간제 시간)만 낸다. 연도가 없으면 서버가 DM을 처리한 날(KST)을 기준으로 2개월 전부터 10개월 뒤 사이에 들어가는 연도로 정하고 `yearInferred`와 확인사항을 남긴다. 접수 시작보다 앞선 추정 날짜는 다음 해로 옮긴다. 마감 시간이 없으면 추정하지 않고 확인사항에 적는다.
- **링크:** 모델이 낸 URL 중 받은 본문·메시지에 그대로 있는 것만 공식 공고·지원 링크로 채택한다.
- **저장:** 레시피와 같은 임시 방식으로 `factchecks`에 `topic='contest'`, `verdict=null`, `claim=공고명`, `reason=JSON.stringify({contest,sourceUrl})`. DB 변경 없음.
- **화면:** 모집 상태(모집 예정·모집 중·마감·마감일 미확인)와 D-day, 일정의 지남·진행 중·예정은 저장하지 않고 화면을 열 때 KST로 계산한다. `dashboard-live.js`가 디자인의 contest 항목(`host`, `organizer`, `dday`, `deadline`, `elig`, `schedule`, `submit`, `process`, `benefit`, `noticeUrl`, `applyUrl`)으로 변환하고, 홈의 ‘다가오는 일정’(60일 이내)과 상세의 ‘캘린더에 추가’(Google 캘린더 링크)를 실제 데이터로 채운다.

검증: `node --test contest.test.mjs content-choices.test.mjs server.test.mjs`. 실제 공모전·대외활동 원본으로 운영 Gemini 결과를 확인하는 작업은 아직 하지 않았다.

## 전시·팝업 구현

- `exhibit.mjs`: 전시 전용 프롬프트(v2)와 Gemini 1회 호출, DM 렌더링. 공모전 처리기가 kind=exhibit으로 판별하면 이미 받아 둔 이미지·영상을 그대로 넘겨받는다(다시 다운로드하지 않음). 이미지·영상 앞에 `[이미지N]`·`[영상N]` 번호표를 붙여 evidence가 가리키게 한다.
- `public/js/exhibit-data.js`: 서버·브라우저 공용 v1 구조 검증과 보기 계산.
  - 모델은 원본에 있는 값만 채우고 없으면 null이다. 화면의 "운영 시간 미기재" 같은 문구는 코드가 붙인다.
  - 링크는 받은 본문·메시지에 실제로 있는 것만 남긴다. 이미지 속 링크는 확인할 수 없어 버리고 확인사항에 적는다.
  - 원문 날짜(`dateRaw`)의 요일이 날짜와 다르면 날짜는 그대로 두고 확인사항에 적는다. 연도를 추정했으면 표시한다.
  - 진행 상태(예정·진행 중·종료), 기간 문구, 지도 검색 링크, 방문 가능 날짜는 볼 때 KST 기준으로 계산하고 저장하지 않는다. 방문 날짜는 휴무가 "매주 월요일"처럼 매주 반복되는 표현일 때만 계산한다.
- 웹 보충(2단계): 게시물에 없는 운영 시간·휴무일·주소·입장료·예약·관람 조건·공식/예약 링크만 찾는다. 전시마다 Gemini google_search 그라운딩으로 검색 1회(모델의 답변은 버리고 실제 방문한 groundingChunks URL만 사용) → 코드가 최대 4개 열기 → 전시명·작가·장소명이 본문에 있는 페이지만 남기고 안내 문장 발췌 → Gemini 1회(전체 전시 한 번에)가 빈칸별 값·출처 페이지·원문 인용을 고른다.
  - 코드가 인용이 실제 페이지에 있는지(공백 무시) 확인하고, 없으면 버린다. 이미 채워진 칸은 덮어쓰지 않고, 다른 정보는 conflicts에 남긴다.
  - 장소 일반 안내(basis=venue)로는 운영 시간·휴무일·주소만 채운다. 링크는 열어 본 페이지 주소이거나 그 본문에 있는 것만 받는다.
  - Bing RSS는 갤러리·전시 질의에 무관한 결과(구글 서비스 홈, 앱 소개 등)만 줘서 쓰지 않는다(@DeonNlTk-Hq 8곳 진단).
  - 결과는 `event.web[필드] = {value,url,title,quote,basis}`로 따로 저장하고, 화면에는 "(웹 확인)", DM에는 `*`와 출처 링크로 표시한다. 검색이 실패해도 게시물만으로 만든 결과는 그대로 보낸다.
- 한 게시물에 전시가 여러 개면(목록형 카드뉴스) 한 행에 events 배열로 저장하고, 대시보드에서는 전시마다 항목(`fc42`, `fc42-2`…)으로 보여준다. 삭제는 게시물 단위다.
- 저장: `topic='exhibit'`, `claim=첫 전시명(외 N곳)`, `reason=JSON.stringify({exhibit,sourceUrl})`. DB 변경 없음.
- 대시보드: 상세 화면의 "일정에 추가"는 고른 날짜의 Google Calendar 링크를 연다. 홈 "다가오는 일정"에 60일 안의 전시 종료일이 들어간다.

## 레시피 구현

- `recipe.mjs`: 프롬프트, Gemini 이미지·영상·본문 동시 분석, DM 렌더링. 첫 레시피 정리와 함께 가벼운 목록 호출(`RECIPE_LIST_SYSTEM`, thinking low)로 레시피 개수를 센다. 레시피 모음 게시물이면 두 번째부터 최대 5개까지 `<focus>`로 하나씩 병렬 정리해 `parts`로 돌려주고, 서버는 레시피마다 `factchecks` 한 건씩 저장하고, 받는 방식 설정과 관계없이 안내 한 줄과 레시피별 개인 링크만 DM으로 보낸다(일부 저장이 실패하면 전체 내용 DM). 일부만 실패하면 성공한 레시피는 저장하고 첫 DM에 실패한 이름을 알린다.
- 모델이 배열로 답하면 첫 레시피를 쓰고, 길이 제한을 넘는 문자열은 잘라서 검증한다(빈 값·누락은 그대로 실패). 실패는 `recipe_failed` 로그에 단계(`list`, `recipe_N`, `result`)와 오류 종류만 남긴다.
- `public/js/recipe-data.js`: 서버·클라이언트 공용 v1 구조 검증. 재료40개·단계30개·팁10개로 제한한다.
- `media-pipeline.mjs`: 기존 최대10개 원본 확보, 전체 파일 확보 실패 시 분석 중단. 준비한 원본은 모델 호출이 끝난 후 finally에서 삭제한다.
- `content-choices.mjs`와 `dm-assistant.mjs`: 티켓의 원본과 action으로 분기. 일반 대화·팩트체크는 유지한다.

영상은 자막·음성 전사만 넘기지 않고 실제 MP4를 이미지·본문과 함께 전달한다. 물·기름·양념·고명도 확인한다. 숫자가 없으면 임의로 계량하지 않고, 선택 재료도 분량이 없으면 null이다. 영양표 계산 인분을 실제 레시피 인분으로 옮기지 않는다. 전체 소요시간과 단계 조리시간, 영상 재생 시각을 구별한다.

각 재료·단계·팁에는 `evidence`가 있다. 원문 계량이 서로 다르면 양쪽 값을 `quantity`에, 출처별 차이는 `conflict`와 `checks`에 보존한다. 명확한 단일 지속시간만 조리 타이머로 연결하며 범위와 영상 타임코드는 자동 타이머로 바꾸지 않는다.

## 맛집 구현

DM 공유 후 네 번째 버튼 **‘맛집 정리’**(`content:v1:restaurant:<티켓>`)로 실행한다. 한 번의 Gemini 호출이 이미지(메뉴판·외관·음식 사진 속 글자)·영상·본문을 함께 읽는다. 게시물 하나에 가게가 여러 곳이면 최대 10곳을 각각 정리한다.

- `restaurant.mjs`: 프롬프트(추측 금지, 원문 가격 그대로, 링크는 본문에 있는 것만), 처리기, DM 렌더링, 접수 안내 문구.
- `public/js/restaurant-data.js`(서버·브라우저 공용): 모델 출력 정규화(분류는 정해진 10개, 그 밖은 `기타`), 가격 파싱(`12,000원`·`1만2천원`·`1.5만원`은 숫자로, 범위·`시가`·여러 숫자는 null이며 원문은 항상 보존), 저장 직전 재검증, DB 행 → 화면 값, 네이버·카카오·Google 지도 **검색 링크**(API 키·위치 권한 없음).
- **저장(타입 테이블):** 다른 유형처럼 `factchecks`에 결과 행(`topic='restaurant'`)을 두므로 `/items/fc<ID>`, DM 발송 상태, 보유 기간, 계정 삭제가 그대로 적용된다. 가게는 `restaurants`, 메뉴는 `restaurant_menus`에 저장하고 부모가 지워지면 함께 지워진다. 서버만 실행할 수 있는 `save_restaurant_result` RPC가 결과 행·가게·메뉴를 **한 트랜잭션**으로 저장한다. RLS로 로그인한 회원은 자기 연결 계정의 가게·메뉴만 읽는다. 검색·관심 색인은 `reason` JSON에 둔다.
- **화면:** 대시보드는 `factchecks` 조회에 `restaurants(…, restaurant_menus(…))`를 함께 불러와 가게마다 항목(`fc42`, `fc42-2`…)을 만든다. 디자인 원본(데스크톱·모바일)에 `맛집` 유형(청록 `#14B8A6` 점·구슬, 필터·사이드바·홈 예시·유형 선택)과 상세(한눈에 보기 / 위치·지도 / 메뉴·가격 / 이용 정보)를 추가했다. 지도는 전시 화면과 같은 그림 지도 카드와 외부 지도 버튼이다. 데모에 가상 맛집 `m1`을 추가했다.
- **아직 없음:** 웹 보충(주소·영업 시간). 맛집 정보 페이지(네이버 플레이스·카카오맵·네이버 블로그)는 서버가 본문 텍스트로 읽기 어려운 구조라 별도 검증 후 붙인다.

검증: `node --test restaurant.test.mjs content-choices.test.mjs server.test.mjs dashboard-frontend.test.mjs`. 실제 맛집 원본으로 운영 Gemini 결과를 확인하는 작업은 아직 하지 않았다.

## 취향공간 구현

DM 공유 후 다섯 번째 버튼 **‘취향공간 정리’**(`content:v1:space:<티켓>`)로 실행한다. 독립서점·소품샵·편집숍·문구점·빈티지숍·LP숍·공방·갤러리·사진관·꽃집·북카페처럼 취향을 따라 찾아가는 공간이 대상이다. 맛집과 같은 흐름(한 번의 Gemini 호출, 추측 금지, 링크는 본문에 있는 것만, 최대 10곳)이고 메뉴·가격대만 뺐다.

- `space.mjs`: 프롬프트, 처리기, DM 렌더링, 접수 안내 문구(`SPACE_ACK`).
- `public/js/space-data.js`(서버·브라우저 공용): 정규화(분류는 정해진 11개, 그 밖은 `기타`), 저장 전·표시 전 재검증, 목록 한 줄 요약. 지도 검색 링크는 맛집의 `mapLinks`를 그대로 쓴다.
- **저장(v1 JSON):** 전시·공모전처럼 `factchecks`에 `topic='space'`, `verdict=null`, `reason=JSON.stringify({space,sourceUrl,contentIndex})`로 저장한다. **DB 마이그레이션 없음.** 맛집처럼 전용 테이블이 필요해지면 `save_restaurant_result`와 같은 방식으로 옮기면 된다.

## 저장·화면 연결

기존 `factchecks` 테이블의 RLS와 `/items/fc<ID>` 경로를 재사용한다. 레시피는 `topic='recipe'`, `verdict=null`, `claim=요리명`, `reason=JSON.stringify({recipe,sourceUrl})`로 저장한다. v1 JSON에는 모든 구조화 필드를 보존하고 기존 뉴스 이유의 2000자 자르기를 적용하지 않는다. DB 마이그레이션과 권한 변경은 없다. 팀원이 통합 콘텐츠 스키마를 확정하면 이 임시 저장 형태를 타입 컬럼으로 이전한다.

프론트는 topic과 version을 확인해 기존 레시피 상세·재료 체크·조리 모드로 매핑한다. JSON이 깨지거나 지원하지 않는 버전이면 목록에서 제외한다. 원본 주소가 없는 직접 CDN 영상도 분석할 수 있고 원본 보기 링크만 생략한다. 실패·조리법 없음은 성공 결과로 저장하지 않는다.
